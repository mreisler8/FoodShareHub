Phase 1 — Database Guardrails (Systemic Prevention)
Migrations (/server/db/migrations/*):

Canonical identity

restaurants keeps id (PK) and unique nullable google_place_id.

If you need many-to-one mapping historically, create:

sql

CREATE TABLE IF NOT EXISTS restaurant_place_map (
  restaurant_id INT REFERENCES restaurants(id) ON DELETE CASCADE,
  google_place_id TEXT UNIQUE,
  PRIMARY KEY (restaurant_id, google_place_id)
);
Backfill restaurant_place_map from existing data where possible.

Ratings referential integrity

Ratings must reference restaurant_id only (FK).

If a google_place_id column still exists in ratings, mark deprecated and stop reading it in API.

Phase 2 — Identity Resolution + Google Places Hand-off (the heart of it)
Files: server/services/identity.ts, server/routes/restaurants.ts, server/services/google-places.ts

2.1 Identity Resolver (single source of truth)
Create resolveRestaurantCanonicalId({ restaurantId?, googlePlaceId? }):

If restaurantId given → look up its google_place_id and return { restaurantId, googlePlaceId }.

If only googlePlaceId given:

Lookup restaurant_place_map/restaurants.

If not found, create a restaurant row with minimal denormalized fields from Places (name, formatted address, lat/lng), assign google_place_id, and return its new restaurantId.

If a request contains both and they don’t match → throw 409 (when FEATURE_STRICT_IDENTITY).

Always return a canonical restaurantId.

Log line (one per request that uses placeId):

Copy
Edit
IDENTITY_RESOLVE placeId=XXX -> restaurantId=26 created=false
2.2 Google Places integration (timeouts + cache + circuit breaker)
Do not directly use Places data for ratings/score keys. Use Places only to:

Enrich the restaurant row on first touch.

Hydrate hero image, metadata, etc.

Add:

Timeout (e.g., 800ms) & circuit breaker for getPlaceDetails(placeId) when FEATURE_PLACES_TIMEOUTS is true.

Cache (5–10 min) keyed by places:detail:{googlePlaceId}.

If Places fails → keep page functional by showing DB data; never block the identity resolution.

Phase 3 — Ratings: Strict Binding + No Fallback
Files: server/routes/ratings.ts, server/services/ratings.ts, client/src/components/ratings/QuickRateModal.tsx

All reads/writes go through identity resolver, then operate by restaurantId only.

If no rating for that user+restaurant → return { exists:false }.
Never fallback to another restaurant’s rating via placeId when FEATURE_DISABLE_RATING_FALLBACK is true.

On write: persist restaurant_id, return payload including { restaurantId, restaurantName, googlePlaceId }.

In production, filter out is_test = true rows.

Phase 4 — Circle Score: One Endpoint, One Cache Key
Files: server/routes/circle-score.ts, client/src/components/.../useCircleScore.ts, client/src/pages/RestaurantDetailPage.tsx

Unified endpoint for new code:

GET /api/restaurant/:restaurantId/circle-score

If a legacy path offers placeId, resolve to restaurantId then call the unified service; log a one-time deprecation notice.

Server cache key: circleScore:{restaurantId} only

Invalidate circleScore:{restaurantId} when a rating for that restaurant is written/updated.

Client hook: useCircleScore(restaurantId)

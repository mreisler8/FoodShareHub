2) Visibility — Single Source of Truth (Resolve Conflicts)

Problem (from audits): isPublic, makePublic, shareWithCircle, and visibility (json/string) disagree. Access checks read different fields.

Solution

Migration (additive):

visibility_v2 enum: 'private' | 'public' | 'followers' | 'circle'

visibility_circle_ids int[] (nullable)

Backfill script (idempotent):

If makePublic=true OR isPublic=true → visibility_v2='public'.

Else if shareWithCircle=true AND circleId IS NOT NULL → visibility_v2='circle', visibility_circle_ids=[circleId].

Else if legacy JSON indicates followers → visibility_v2='followers'.

Else → 'private'.

Writes (create/update) when LISTS_VISIBILITY_V2=true:

Accept only { visibility: 'private'|'public'|'followers'|'circle', visibilityCircleIds?: number[] }.

Normalize: if visibility!=='circle' then visibilityCircleIds=null.

Reads (access control) everywhere use only visibility_v2 (+ circle membership checks when 'circle'). Keep reading legacy for backward compatibility if flag is off.

Acceptance

Creating lists in each mode yields correct access control for A/B/C/D.

Private lists invisible to non-owners; circle lists visible only to members of listed circles.

Legacy fields remain readable; writes use visibility_v2 only when flag on.

3) Save/Unsave — Status Endpoint + Reconciliation

Problem: UI checks /api/saved-lists (full collection) → inefficient & racy; mixed endpoints across components.

Solution

Endpoints (auth required; idempotent):

GET /api/lists/:id/save-status → { saved: boolean }

POST /api/lists/:id/save

DELETE /api/lists/:id/save

Frontend:

SaveListButton uses only ['saved-lists', listId] and calls the status endpoint.

Mutations are optimistic; on settle, invalidate ['saved-lists', listId] and ['lists', listId].

Tests

supertest: POST twice returns 200; status flips correctly. DELETE idem.

RTL: icon/state persists after refresh & route change.

Acceptance

Save state consistent across all surfaces (cards, details, feeds) after refresh/navigation.

5) Add Items & Reorder — Confirm Endpoint + Wire UI

Problem: Modal exists; POST path not validated end-to-end.

Backend

POST /api/lists/:id/items body:

{ restaurantId: number; position?: number | null; notes?: string | null; mustTryDishes?: string[] | null }


Auth required; owner/editor only.

Idempotent: if restaurantId already in list → 200 with existing row (no dup).

Positioning: null=append; else insert and shift.

PUT /api/lists/:id/items/reorder:

{ itemIds: number[] } // final order; transactional


Frontend

AddListItemModal → POST; invalidate ['lists', listId, 'items'].

DraggableRestaurantList → optimistic reorder with rollback on error.

Tests

supertest: add same restaurant twice → no duplicates.

RTL: keyboard & mouse reorder; persists after refresh.

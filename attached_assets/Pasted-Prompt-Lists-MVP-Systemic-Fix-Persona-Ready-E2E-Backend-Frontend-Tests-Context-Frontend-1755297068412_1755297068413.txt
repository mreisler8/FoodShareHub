1) Visibility: single source of truth (fix the conflicts)

Problem (from audit): isPublic, makePublic, shareWithCircle, and visibility (json|string) disagree; access checks read different fields.

Solution

Add canonical column (non‑breaking):

Migration: add visibility_v2 (enum: 'private' | 'public' | 'followers' | 'circle') and visibility_circle_ids (int[], nullable).

Backfill script:

If makePublic=true OR isPublic=true → visibility_v2='public'.

Else if shareWithCircle=true AND circleId IS NOT NULL → visibility_v2='circle', visibility_circle_ids=[circleId].

Else if legacy visibility JSON indicates followers → visibility_v2='followers'.

Else → visibility_v2='private'.

Keep legacy fields for read‑only compatibility; stop writing to them when LISTS_VISIBILITY_V2=true.

API writes (create/update) must:

Accept only visibility_v2 + optional visibility_circle_ids.

Normalize/validate: if visibility_v2!=='circle' then visibility_circle_ids=null.

Access control everywhere reads only visibility_v2 (+ circle checks when 'circle'), never legacy booleans.

2) Save/Unsave: add status endpoint + fix reconciliation

Problem: UI checks /api/saved-lists (full collection), causing inefficiency/races. No single‑list status endpoint.

Solution

Endpoints

GET /api/lists/:id/save-status → { saved: boolean } (auth required).

POST /api/lists/:id/save → 200 idempotent; no duplicate saves.

DELETE /api/lists/:id/save → 200 idempotent.

Frontend

SaveListButton should:

Use React Query keys: ['saved-lists', listId].

Read GET /api/lists/:id/save-status.

Use optimistic updates for POST/DELETE and invalidate both ['saved-lists', listId] and ['lists', listId].

Tests

supertest: first POST returns 200, second POST still 200; status flips accordingly. DELETE idem potent.

3) Add Items: confirm endpoint & wire UI

Problem: Add‑item modal exists; POST path not validated end‑to‑end.

Solution

Endpoint (confirm/implement):

POST /api/lists/:id/items body:

{
  "restaurantId": number,
  "position": number | null,
  "notes": string | null,
  "mustTryDishes": string[] | null
}


Server rules:

Auth required; owner or editor.

Idempotency: if same restaurantId already exists on list, return 200 and respond with existing row (no duplicate).

Positioning: if null, append; otherwise place and shift others.

PUT /api/lists/:id/items/reorder for drag‑reorder (array of itemIds in final order), transactional.

Frontend

AddListItemModal → calls POST; on success invalidate ['lists', listId, 'items'].

DraggableRestaurantList → uses reorder mutation with optimistic update and rollback on error (React Query).
